# Pierwsze zlecenie dla Claude Code — TibiaAI

Pracujesz w projekcie TibiaAIServer. Chcę dziś uruchomić prywatny lokalny świat OpenTibia i rozpocząć rzeczywistą integrację autonomicznego NPC. Przeczytaj CLAUDE.md oraz wszystkie pliki DOCS przed zmianami. Zachowaj istniejące materiały. Ten pakiet jest specyfikacją, nie dowodem działającego wdrożenia.

Docelowe doświadczenie: wchodzę do gry, spotykam strażnika Ardana. Patroluje kilka punktów, reaguje na lokalne powitanie, przerywa patrol po kontrolowanym alarmie, ostrzega i wraca na trasę. Później pamięta nasze spotkanie po restarcie Brain. Każde zdarzenie i wynik działania można prześledzić w dzienniku. Najpierw tryb reguł, model językowy dopiero gdy działa cały przepływ.

## Wykonaj teraz

1. **Rozpoznaj środowisko bez zmian globalnych.** Sprawdź katalog, git status, istniejące dokumenty, system, dostęp do Windows/WSL, Docker/Compose, Node/pnpm, wolne porty, RAM/dysk. Nie instaluj drugiej bazy w XAMPP ani nie zmieniaj jego usług. Projekt może być pod C:\xampp\htdocs\projects\tibia\TibiaAIServer — sprawdź ryzyko udostępniania plików przez Apache, nie przenoś katalogu samowolnie. Zapisz wynik w iteracji 0001 i STATUS.

2. **Ustal jeden zgodny zestaw.** Preferuj oficjalny Canary i OTClient Redemption. Sprawdź SOURCES.md, aktualne źródła i dokumentację wybranego commita. Obecny main ma quickstart z MariaDB, MyAAC i osobnym login-server; wydanie v3.6.1 i dokumentacja main różnią się wersją klienta. Nie łącz przypadkowo binarki release, skryptów main i najnowszych grafik. Przypnij źródło, runtime image digest, klienta, protokół, datapack, mapę i assets w COMPATIBILITY. Jeśli nie możesz potwierdzić pozycji, zapisz BLOCKED zamiast zgadywać. Użycie bieżącego main jest dopuszczalne tylko jako konkretny commit, zgodny z runtime. TFS to alternatywa po zapisaniu konkretnego blokera Canary, nie drugi równoległy projekt.

3. **Uruchom fundament.** Przygotuj lokalny Compose na podstawie zweryfikowanej konfiguracji upstream; unikalna nazwa projektu, osobne wolumeny, baza bez portu hosta, porty aplikacji związane z 127.0.0.1. Zbadaj wyrenderowane `docker compose config`, żeby override nie pozostawił dodatkowych publicznych mapowań. Nie odpalaj nieprzeczytanych skryptów czyszczących Docker. Przygotuj powtarzalne start/stop/status/logs bez usuwania danych. Zapisz dokładne instrukcje PowerShell i lokalizację ich wykonania w RUNBOOK. Sprawdź bazę, start mapy i login endpoint. Jeśli potrzebujesz instalacji Docker Desktop/WSL albo ręcznego dostarczenia zgodnych assets, podaj dokładnie brakujący element i kontynuuj niezależne prace. Nie udawaj, że kontener w zdalnej sesji jest serwerem na moim Windows.

4. **Przygotuj klienta i realny test wejścia.** Korzystaj z oficjalnego repo/release OTClient, dopasuj adres logowania, protokół i assets. Rozróżnij HTTP login i port świata. Nie zakładaj, że localhost wewnątrz kontenera oznacza host Windows. Jeśli możesz uruchomić GUI, przetestuj wejście i ruch. W przeciwnym razie daj mi krótką instrukcję i oznacz test GUI NOT RUN. Nie nazywaj odpowiedzi HTTP dowodem wejścia do gry.

5. **Dodaj Ardana w Lua.** Użyj małego obszaru istniejącej mapy i ręcznie zweryfikowanych współrzędnych; nie buduj dziś całej mapy. Sprawdź bindingi NPC/Creature w konkretnym źródle. Zaimplementuj deterministyczny patrol, reakcję na powitanie, kontrolowany alarm administratora, ostrzeżenie i powrót. Bez walki, lootu i handlu. Brak przejścia ma dawać timeout/failure, a nie teleport. Normalne losowe chodzenie NPC nie może walczyć z naszym kontrolerem. Alarm ma być zdarzeniem testowym, nie udawaną detekcją prawdziwego potwora.

6. **Zrób krótki eksperyment transportu.** Sprawdź, czy dostępny jest faktyczny asynchroniczny transport Lua↔Brain z obsługą odpowiedzi. Webhook.sendMessage nie jest dowodem dwukierunkowego HTTP. Jeśli transportu nie ma, opisz ADR i wybierz minimalny most: ograniczony lokalny mailbox JSON z atomowym zapisem/odczytem małych plików po sprawdzeniu I/O Lua, albo mały adapter C++ asynchroniczny. Nie przebudowuj całego silnika w ciemno. Udowodnij jeden event → Brain → komenda → walidacja → wynik. Jeśli ten etap blokuje się, pozostaw działającego Ardana w Lua i dokładny blocker, nie atrapę integracji.

7. **Gdy fundament działa, dodaj cienki przekrój Brain.** Node.js/TypeScript, walidacja kontraktów, rules provider i SQLite. Jeden agent, jeden typ pamięci spotkania, say + patrol jako działania. Zapisz player GUID zamiast chwilowego creature ID. Odtwórz pamięć po restarcie. Potwierdź odrzucenie duplikatu, starego session ID i nieznanej akcji oraz działanie gry po wyłączeniu Brain. Nie podłączaj płatnego modelu ani nie pobieraj wielkiego modelu lokalnego bez ustalenia wyboru i limitu kosztów.

## Warunki pracy
Działaj etapami i realizuj możliwe kroki zamiast kończyć na planie. Nie rozbudowuj UI. Nie deklaruj, że etap jest zakończony bez dowodu. Jeśli czas zajmie instalacja i klient, uczciwie zakończ na M0/M1 — to wartościowy wynik, nie zastępuj go symulacją w przeglądarce. Po każdej iteracji aktualizuj dokumentację według CLAUDE.md. Przed większą zmianą architektury zapisz decyzję i powód. Nie pytaj o rutynowe odwracalne kroki. Pytaj tylko o faktyczny brak danych lub nieodwracalną operację.

Na koniec podaj: listę działających elementów, testy PASS/FAIL/NOT RUN, blokery, dokładną instrukcję co mam teraz uruchomić na Windows, i jedno następne zadanie. Zaktualizuj DOCS/STATUS.md tak, żeby następna sesja kontynuowała pracę bez zgadywania.
